# 여행 데이터 소스

## Decisions

- 다이빙 목적지의 월별 컨디션 등급, 다이빙 요금, 장비 대여료, 리브어보드 요금, 인천 출발 항공 요금대, 숙소 요금대는 저장소 안에 큐레이션된 정적 데이터로 보관한다.
- 데이터는 웹 조사로 수집해 사람이 검토한 뒤 저장소에 커밋한다. 갱신은 수동이다.
- 모든 금액은 실제 예약가가 아니라 조사 시점 기준 요금대로 표기하고, 화면에 기준 시점을 함께 노출한다.

## Boundaries

- 실시간 조회가 필요한 기능(항공권 잔여 좌석, 다이빙샵 예약 가능 여부)은 이 결정의 범위 밖이며, 현재 제품 경계상 다루지 않는다.
- 지도 타일과 다이빙샵 상세 페이지 링크는 외부 서비스를 쓴다. 이 결정은 컨디션·요금 데이터에만 적용된다.
- 구현 시 화면 코드는 목적지 데이터를 별도 모듈(예: 데이터 접근 계층 하나)을 통해서만 읽는다. 그 모듈이 정적 파일을 읽는지 데이터베이스를 조회하는지는 모듈 내부 구현이며, 화면 코드는 이를 몰라야 한다. 이렇게 캡슐화해두면 정적 파일에서 데이터베이스로 옮길 때 그 모듈 내부만 바꾸면 되고, 화면 쪽 코드는 손대지 않는다.

## Why

월별 다이빙 컨디션(시야, 수온, 조류, 대물 시즌)은 어떤 외부 API로도 제공되지 않아 어차피 사람이 조사해 넣어야 한다. 항공 요금만 실시간으로 붙여도 나머지 절반은 정적 데이터로 남으므로, 소스를 하나로 통일하는 편이 일관성과 검증 비용 면에서 낫다. 강의용 템플릿이라 API 키 발급과 요금 청구 없이 바로 돌아가는 것도 중요하다.

## Reconsider when

- 사용자가 실제 예약가와의 괴리를 문제로 지적하기 시작할 때.
- 목적지 수나 갱신 빈도가 정적 파일 수동 편집으로 감당하기 어려운 규모로 늘어날 때. 이때는 데이터 접근 모듈 내부만 데이터베이스 조회로 교체한다.

## Still-rejected alternatives

- Claude API 실시간 생성 — 모델이 없는 다이빙샵이나 틀린 요금을 만들어낼 위험이 있고 같은 조건에서 결과가 매번 달라져 후보지 비교가 성립하지 않는다. 조사된 데이터를 근거로 제시하는 형태로 쓴다면 다시 검토할 수 있다.
- 외부 API 연동(구글맵 Places, 항공권 API) — API 키·요금·할당량 문제가 생기고, 정작 핵심인 월별 컨디션은 API로 나오지 않아 정적 데이터를 병행해야 한다. 실시간 항공 요금이 제품의 핵심 가치가 되면 다시 검토한다.
